# Faithful Translation Specification — `eigon-julia-gen`

**Status:** Implemented v1.2 (Phase 19a.4; mirror generator landed and exercised by the five Julia institutions)
**Changes from v1.1 → v1.2:** Per-module codec registries `_eigenius_decoders` / `_eigenius_encoders` (§8.5) — pinned so the worker-side `CallRuntimeMethod` dispatcher can discover decoders/encoders across loaded mirror modules without per-module knowledge. World-age rule for codec invocation pinned in §8.5 (`Base.invokelatest` required when codecs may have been loaded after the dispatch frame's world).
**Changes from v1 → v1.1:** Subclass hierarchy emission (universal abstract+struct pair, single-supertype enforced); `_id` round-trip via reserved field on every struct (§7, §8.4); polymorphic `class_types` as `Union{AbstractC1, …}` with codec dispatch helpers (§4, §8.3); `core:format` IRI passthrough for non-standard formats (§9.3); pattern anchoring made explicit in the validator (§9.4); cycle detection on closure + `subclass_of` (§3.3, §11.1); `short_name` conflict detection in transitive field set (§11.1); multi-`is_a` reframed as a substrate concern, not an information loss (§8.4).
**Scope:** The exact, byte-level contract between Eigon class structure (as resolved against an ontology layer in the chain) and the Julia source emitted by the substrate's mirror generator. Pins what the generator promises to produce so an auditor with the layer chain and the spec can re-derive byte-identical mirror source without reading the generator's Rust code.
**Related:** [`d26-runtime-substrate.md`](d26-runtime-substrate.md) §7 (the language-agnostic `RuntimePackageMirror` model and faithful-translation framework), [`d27-julia-institutions.md`](d27-julia-institutions.md) §3 (the Julia integration's framing of the generator), [`implementation-plan.md`](implementation-plan.md) Phase 19a.3 (the generator's implementation milestone). The hand-authored shared package the generated source imports lives at [`julia/common/EigeniusJuliaCommon/`](../../julia/common/EigeniusJuliaCommon/).

## 1. Purpose

The mirror generator is **substrate Rust code** that runs inside `JuliaLanguageRuntime::build_environment_image` (D26 §9.2). It walks the chain's ontology layer and emits a Julia *package* the worker `using`-imports — every Eigon class in the closure becomes a Julia struct with codecs and validating constructors. The generator's output is committed back to the chain as a `RuntimePackageMirror` resource (D26 §5.4) and baked into the env image.

Auditability of the mirror does **not** rely on the generator being a separate binary or on inspecting its Rust source. It relies on this specification: given the spec, the layer chain, and the substrate's pinned `generator_content_hash`, an auditor MUST be able to re-derive the same Julia source byte-for-byte. This document is the load-bearing TCB artifact alongside the generator binary's content hash.

When the spec and the implementation disagree, the implementation is wrong. When the spec underspecifies a behavior, both this doc and the generator are wrong — the spec is the source of truth.

### 1.1 Conformance levels

A generator implementation conforms to **D29 v1** if it emits the constructs defined in §§4–10 for inputs in the v1 supported subset (§11) and emits a typed `MirrorGeneratorError::UnrepresentableClass` for inputs outside it. The v1 supported subset deliberately excludes constructs that are part of the long-term faithful-translation table (D27 §3.3) but require generator features not present in 19a.3 — those are pinned as **planned** in §11.2 with an implementation milestone.

### 1.2 Non-goals

- **Predicate translation.** Format constraints, `requires` / `recommends`, `min_value` / `max_value` are checked at construction time as runtime validation. They are not encoded as Julia types or refinement conditions. Predicate translation is the Lean integration's job (D28 / D30, `EigonFFI`).
- **Behavioural specification.** What the user code *does* with a mirror struct — institution morphisms, query handlers, worker procedures — is not the generator's concern. The generator emits only structural projection: types, codecs, validators.
- **Round-tripping `@id`.** A resource's IRI is the chain's identity for it, not its data. Decode/encode through the mirror is intentionally lossy on `@id` (§7.4).

## 2. Output package layout

Each invocation of the generator produces exactly one Julia package, regardless of how many Eigon classes are in the closure. The package contains:

```
EigeniusMirror/
├── Project.toml
└── src/
    └── EigeniusMirror.jl
```

### 2.1 Package metadata (`Project.toml`)

The `Project.toml` is the literal text:

```toml
# Auto-generated by eigon-julia-gen — DO NOT EDIT.
name = "EigeniusMirror"
uuid = "8a7b6c5d-4e3f-4a1b-9c8d-7e6f5a4b3c2d"
authors = ["The Eigenius Authors"]
version = "0.1.0"

[deps]
EigeniusJuliaCommon = "9c8e7a4e-1f2b-4c3d-9e5f-6a7b8c9d0e1f"

[compat]
julia = "1.10"
```

Fields are pinned, not derived from the chain:

- `name = "EigeniusMirror"` — the package name and module name are fixed for v1. Multi-mirror-per-runtime support (one mirror per `RuntimeEnvironment`) lands later (D27 §3.6 future-work). Until then, every `RuntimeEnvironment` images its own copy of this package.
- `uuid` — fixed v4-shaped UUID, stable across runs. The UUID is part of the spec, not regenerated per build.
- `version` — fixed `"0.1.0"` for v1. Bumps follow the spec version, not the chain's content.
- `[deps]` — exactly one entry: `EigeniusJuliaCommon`, pinned at the UUID declared in [`julia/common/EigeniusJuliaCommon/Project.toml`](../../julia/common/EigeniusJuliaCommon/Project.toml). The UUID is a literal in this spec; if the hand-authored package's UUID changes, the spec and generator update together.
- `[compat] julia = "1.10"` — the generated package targets Julia 1.10+.

### 2.2 Module file (`src/EigeniusMirror.jl`)

The module file's structure, byte-by-byte:

```
# Auto-generated by eigon-julia-gen — DO NOT EDIT.
# Regenerate via the substrate's image-build pipeline.
# source_layer: <layer IRI>
# mirrored_classes:
#   - <class IRI 1>
#   - <class IRI 2>
#   ⋮

module EigeniusMirror

using EigeniusJuliaCommon: validate_min_value, validate_max_value, validate_min_length, validate_max_length, validate_pattern, validate_format

<per-class blocks, in topological order — §6>

export <comma-separated list of Class, decode_Class, encode_Class for each class>

end # module EigeniusMirror
```

The header carries the source layer IRI and the closure's class IRIs in topological order — same content the resource's `mirrored_classes` and `source_layer` properties carry, duplicated as comments so a reader of the file alone has full provenance.

The `using` import line is fixed; new validators added to `EigeniusJuliaCommon` show up here only after both the hand-authored package and this spec are updated.

### 2.3 What's deliberately not in the output

- No `Manifest.toml`. The package's manifest is resolved at image-build time inside `Pkg.develop` against the worker's project.
- No tests, examples, or top-level scripts.
- No per-class file split. v1 collapses to one file because Julia parses per-file as a unit and one file is the simplest deterministic emission target. Per-class splitting is a future-work item (D27 §3.6) when closure size makes one file unwieldy; out of scope for D29 v1.
- No re-exports of `EigeniusJuliaCommon` symbols. User code that wants validators imports `EigeniusJuliaCommon` directly.

## 3. Closure walk

Given a seed of class IRIs, the generator walks the chain to compute the *closure*: every class transitively reachable through structural references. The closure is what gets mirrored — the `mirrored_classes` property on the resulting `RuntimePackageMirror` lists the closure, sorted by IRI for determinism.

### 3.1 Reachability rules

A class C is in the closure iff:

1. C is in the seed, **or**
2. There exists a class C' in the closure such that C' has a property P (in `requires` ∪ `recommends`) with `data_type ∈ {resource, resource_array}` and `class_types` containing C.

Note that **all entries** in a property's `class_types` are walked. Multi-class polymorphic properties pull every named class into the closure — none are silently dropped.

The closure is a fixpoint of these rules over the class graph, computed by a worklist algorithm seeded with the input. Cycles in the class graph are tolerated by the walker (visited set), and rejected later in topological-order resolution (§3.3).

### 3.2 Subclass closure

`core:subclass_of` is part of the structural closure: a class C with `subclass_of: [P]` pulls P into the closure transitively, just as a property's `class_types` does. The generator walks both edge sets in the same closure pass.

Multi-supertype is rejected. If a class declares `subclass_of` with more than one entry, the generator returns `MirrorGeneratorError::UnrepresentableClass` naming the offending class — Julia abstract types support only single inheritance and v1.1 does not synthesize intersection types. (Future-work in §11.2.)

The closure-walking rule subsumes the v1 restriction. v1.1 emission shape (§7) places every class C in an abstract+struct pair: `abstract type AbstractC end` carries the hierarchy edge (`<: AbstractParent` when C declares `subclass_of`), and `struct C <: AbstractC` carries the data fields. A class participating in `subclass_of` produces both pieces just like any other class — there is no "abstract-only" or "concrete-only" branch.

### 3.3 Topological order

After closure computation, classes are emitted in dependency order: a struct that has a field of type `<C>` (or `Vector{<C>}` etc.) must be defined after C. The emission order is determined by depth-first traversal:

1. Start from each class IRI in **sorted order** (BTreeMap key order).
2. Visit dependencies (fields whose Julia type references another mirror struct) first, recursively.
3. Append the current class to the order after dependencies are done.
4. A `visited` set short-circuits the visit so each class lands exactly once.

This produces a stable order for any closure with no cycles. Stable on tie because the seed is sorted by IRI before traversal starts.

**Cyclic class references are rejected**, in two places: cycles via property `class_types` (the field-dependency graph) and cycles via `subclass_of` (the inheritance graph). Both produce `MirrorGeneratorError::UnrepresentableClass` naming the offending class. Julia's `struct` declaration form requires forward references to be resolved at parse time and abstract types form a strict tree with no cycles; mutable-struct + forward-declaration workarounds add nontrivial spec surface and are deferred. v1.1 callers must factor cycles out of the seed (typically by extracting an interface class).

## 4. Faithful type translation

For each Eigon property `P` with `data_type T` (and, where relevant, `class_types` or `element_type`), the property's field in the enclosing class's mirror struct has the Julia type defined by this table. **Class references in field positions always render as the `Abstract<C>` slot** of the abstract+struct pair (§3.2 / §7), so a field declared with `class_types: [C]` accepts `C` and any concrete subclass of C uniformly.

| Eigon `data_type` | Side property | Julia type |
|---|---|---|
| `core:string` | — | `String` |
| `core:integer` | — | `Int64` |
| `core:float` | — | `Float64` |
| `core:boolean` | — | `Bool` |
| `core:json` | — | `Any` |
| `core:resource` | `class_types: [C]` (singleton) | `AbstractC` |
| `core:resource` | `class_types: [C₁, …, Cₙ]` (n ≥ 2) | `Union{AbstractC₁, …, AbstractCₙ}` |
| `core:resource_array` | `class_types: [C]` (singleton) | `Vector{AbstractC}` |
| `core:resource_array` | `class_types: [C₁, …, Cₙ]` (n ≥ 2) | `Vector{Union{AbstractC₁, …, AbstractCₙ}}` |
| `core:value_array` | `element_type: core:string` | `Vector{String}` |
| `core:value_array` | `element_type: core:integer` | `Vector{Int64}` |
| `core:value_array` | `element_type: core:float` | `Vector{Float64}` |
| `core:value_array` | `element_type: core:boolean` | `Vector{Bool}` |
| `core:value_array` | `element_type: core:json` | `Vector{Any}` |

Order of `class_types` IRIs in a `Union` is the IRI sort order, **not** the source order — this is a deviation from the chain (chains preserve declaration order on `Value::Array`). The deviation is intentional: union types in Julia are nominal but order-sensitive in `repr`/printing, so byte-identical generation requires a canonical ordering. Sort by IRI is the canonical choice the generator already uses for closure determinism.

### 4.1 Required vs. recommended

- A property in `core:requires` produces a **required positional field** with the bare type from §4.
- A property in `core:recommends` produces an **optional keyword field** with the type `Union{T, Nothing}`, defaulting to `nothing`.

A property listed in both `requires` and `recommends` is malformed at the ontology level; the generator's behavior is unspecified. Ontology validators must catch this upstream.

### 4.2 Unsupported `data_type` values

Any `data_type` not in the §4 table — including future kernel types and `core:resource` / `core:resource_array` with empty `class_types` — produces a `MirrorGeneratorError::UnrepresentableClass` naming the offending class and property. The mirror as a whole fails; partial mirrors are not a thing.

---

## 5. Struct field ordering

A class's struct has its required fields first (in the order declared in `requires`), followed by its recommended fields (in the order declared in `recommends`).

Within `requires` / `recommends`, the order is **the order the property IRIs appear in the chain's resource representation**. The kernel's canonical Resource representation uses BTreeMap-sorted property keys, so practical ontology authors get IRI-sorted ordering; ontologies that explicitly serialise an ordered `requires` array get that order preserved. Either way, a fixpoint over the chain produces a stable, deterministic field list.

---

## 6. Per-class emission

For each class C in topological order, the module body contains three definitions, separated by single blank lines:

1. The `struct C` declaration (§7).
2. `decode_C` (§8.1).
3. `encode_C` (§8.2).

Each block ends with a single trailing newline, then a blank line before the next. The exports line at the bottom of the module is generated once after all classes are emitted (§2.2).

## 7. Abstract type and struct declaration

Per §3.2, every class C in the closure produces an abstract+struct pair. Abstract types are emitted in a single block before any concrete struct (so abstract supertype references resolve at parse time); concrete structs follow in field-dependency topological order (§3.3). Codecs and helpers are emitted alongside their concrete struct.

### 7.1 Abstract type declarations

For each class C in `subclass_of`-topological order (parent before child, IRI sort tie-break):

```
abstract type AbstractC end
```

If C declares `subclass_of: [P]`:

```
abstract type AbstractC <: AbstractP end
```

The abstract types form a strict tree (cycles rejected by §3.3). Multi-supertype rejected by §3.2.

### 7.2 Concrete struct declaration

For each class C, after all abstract types are declared:

```
struct C <: AbstractC
    <transitive required fields>
    <transitive recommended fields>
    _id::Union{String, Nothing}

    function C(
        <required positional args>,
        ...
        ;
        <recommended keyword args>,
        ...
        _id::Union{String, Nothing} = nothing,
    )
        <required-field validation>
        <gated recommended-field validation>
        new(<required>, <recommended>, _id)
    end
end
```

Notes:

- The struct's `<: AbstractC` clause anchors the data slot under its abstract counterpart. Since every class has both, this is unconditional.
- **`_id`** is the mirror-managed `@id` round-trip slot (§8.4). Always emitted as the last struct field; always a kwarg with default `nothing` in the constructor (last among kwargs, after recommended properties); always passed to `new(...)` last.
- `<transitive required fields>` is the union of `requires` from C's `subclass_of` chain root-to-leaf, with duplicate property IRIs deduplicated (first-declared wins). Same rule for recommended.

### 7.3 Field type rendering

Field types render as defined in §4. References to other mirror classes render as the `Abstract<C>` slot — never the concrete struct name — so any concrete subtype assigned to the field type-checks. Sanitisation into a Julia identifier is unnecessary for short names; the ontology validator pins `short_name` to a Julia-safe form (alphanumeric + underscore, leading non-digit). If a class somehow makes it into the closure with a non-conforming `short_name`, the generator's behavior is unspecified — fix the ontology.

### 7.4 Field-set inheritance

For a class C with `subclass_of: [P]`:

- The transitive `requires` field set is `P`'s transitive `requires` followed by C's own `requires`, deduplicated by property IRI (first-declared wins). Same for `recommends`.
- The reserved `_id` slot is part of every class's field set automatically; it does not deduplicate against itself across the chain.
- A `short_name` collision between two distinct property IRIs anywhere in the transitive set is rejected (§11.1).

### 7.5 Empty class

A class with no inherited or own `requires` / `recommends` still produces a struct with the `_id` field and the corresponding kwarg constructor:

```
struct C <: AbstractC
    _id::Union{String, Nothing}

    function C(
        ;
        _id::Union{String, Nothing} = nothing,
    )
        new(_id)
    end
end
```

The leading `;` opens the kwarg section even when no positional args precede it.

### 7.6 The `;` separator in the constructor signature

The kwarg section is **always** present (it carries at minimum `_id`), so the `;` separator after the last required positional arg is unconditional. When no positional args precede, the leading `;` opens the section as in §7.5.

### 7.7 Validation block

Required fields' validation calls (§9) come first, in field-declaration order. Recommended fields' validation calls come second, each gated on `if !isnothing(<field>) ... end`. The `_id` field has no validators in v1.1 — IRI well-formedness is the kernel's responsibility upstream.

### 7.8 The `new(...)` call

Constructs the struct in canonical field order: transitive `requires` first (root-to-leaf, dedup-stable), then transitive `recommends` (same order), then `_id`. The struct's declaration order in §7.2 matches this order; `new(...)` arguments are passed positionally.

## 8. CBOR codec emission

The codecs are responsible for round-tripping a mirror struct through the IRI-keyed `Dict{String, Any}` shape that the substrate's CBOR boundary uses (D26 §7).

### 8.1 `decode_<C>(m::AbstractDict)::<C>`

```
function decode_<C>(m::AbstractDict)::<C>
    <C>(
        <required-field decode expressions>;
        <recommended-field decode expressions>,
    )
end
```

For each required field with property IRI `<iri>`:

- **Primitive type** (`String`, `Int64`, `Float64`, `Bool`, `Any`): `m["<iri>"]`.
- **Mirror struct ref**: `decode_<RefClass>(m["<iri>"])`.
- **`Vector` of primitive**: `m["<iri>"]`.
- **`Vector` of mirror struct ref**: `[decode_<RefClass>(_x) for _x in m["<iri>"]]`.
- **`Union{T₁, …, Tₙ}` of mirror struct refs**: see §8.3.

For each recommended field, the decode expression is wrapped in:

```
<field_name> = (let _v = get(m, "<iri>", nothing); isnothing(_v) ? nothing : (<inner decode of _v>) end),
```

The trailing comma is always emitted; Julia accepts trailing commas in keyword-argument lists.

### 8.2 `encode_<C>(c::<C>)::Dict{String, Any}`

```
function encode_<C>(c::<C>)::Dict{String, Any}
    out = Dict{String, Any}(
        "urn:eigenius:core:is_a" => ["<C IRI>"],
        <required-field encode entries>,
    )
    <recommended-field conditional encode lines>
    return out
end
```

The first entry is always the `is_a` stamp: a single-element `Vector{String}` containing the class's IRI. (Eigon's `is_a` is a list, even when there's one element — matching how `Resource::set` represents `core:is_a` arrays in the chain.)

For each required field:
- Primitive: `"<iri>" => c.<field>`.
- Mirror struct ref: `"<iri>" => encode_<RefClass>(c.<field>)`.
- `Vector` of primitive: `"<iri>" => c.<field>`.
- `Vector` of mirror struct ref: `"<iri>" => [encode_<RefClass>(_x) for _x in c.<field>]`.
- `Union{T₁, …}` of mirror struct refs: see §8.3.

For each recommended field, the conditional is:

```
isnothing(c.<field>) || (out["<iri>"] = <encode expr for c.<field>>)
```

### 8.3 Polymorphic (`Union`) field codecs

A field whose type is `Union{<C₁>, …, <Cₙ>}` (n ≥ 2) requires runtime dispatch in both directions:

- **Encode**: `c.<field>` is one of the `Cᵢ`. Dispatch on `typeof(c.<field>)` to the matching `encode_<Cᵢ>`. The generator emits a per-field helper of the form:
  ```
  _encode_field_<C>_<field>(v) = ...
  ```
  with a `if v isa C₁ encode_C₁(v) elseif … else error("…") end` body, and references it from `encode_<C>`. (Julia's multiple dispatch could subsume this, but a generated helper keeps the emission fully local to the mirror module — no dispatch tables outside the file.)
- **Decode**: a CBOR-decoded resource carries its own `is_a` list. The decoder reads `m["urn:eigenius:core:is_a"]` and dispatches to the matching `decode_<Cᵢ>`. If no `is_a` entry intersects `{C₁, …, Cₙ}`, the decoder raises an `ArgumentError`.

The `Vector{Union{…}}` case is the array-comprehension lifting of the scalar dispatch: `[_decode_field_<C>_<field>(_x) for _x in m["<iri>"]]`.

### 8.4 Information preservation across decode/encode

#### `@id` round-trips via the reserved `_id` slot

Every mirror struct carries a reserved `_id::Union{String, Nothing}` field — kwarg, default `nothing` (§7.2). The codec round-trips it through the JSON-LD-shaped `"@id"` key:

- **Decode** reads `m["@id"]` if present and assigns it to `_id`; otherwise `_id = nothing`.
- **Encode** stamps `out["@id"] = c._id` if `c._id !== nothing`; otherwise the output dict has no `@id` entry.

A chain resource decoded into a struct, mutated, and re-encoded round-trips the IRI faithfully. Worker-constructed values that don't claim an IRI leave `_id` unset and produce IRI-less output dicts; the substrate's commit pipeline (D26 §7.5) is responsible for assigning an IRI before chain commit if one is needed.

#### Multi-`is_a` is delegated to the substrate, not preserved by the mirror

A chain resource may carry `is_a: [C, D, …]` claiming simultaneous instance-of membership in multiple classes (distinct from class-level `subclass_of`). The mirror codec is one-struct-per-resource — a Julia value is exactly one concrete struct type — so multi-`is_a` does not have a faithful Julia struct representation:

- **Encode** stamps `is_a: [<struct's class IRI>]` only — a single-element list naming the concrete struct's own class.
- **Decode** through a Union helper (§8.3) walks the input's `is_a` list in IRI sort order and dispatches on the first match against the helper's enumeration of concrete leaves. Entries in `is_a` that don't appear in the mirror's closure (e.g. epistemic categories like `:Derived`, audit tags, classes outside the seed) are ignored.

This is delegation, not loss. Epistemic categorization belongs to the substrate's commit pipeline — when a worker returns a typed result, the substrate stamps the appropriate epistemic category onto the committed resource's `is_a` list. The mirror's job is purely structural projection of class-data; epistemic stamping at commit time is the right layer for the policy. (Cross-link to D26: substrate's commit pipeline gains an epistemic-category-stamping pass — `:Derived` for runtime-substrate outputs — as a future-work item, not a D29 concern.)

#### What is genuinely lost

- `is_a` entries beyond the struct's own class are dropped on encode (intended; substrate restamps).
- `is_a` entries from outside the mirror's closure are ignored on decode (intended; not the mirror's domain).
- Worker-side mutation of `_id` is preserved; worker-side mutation of `is_a` is not faithful — the encoder always emits the struct's own class.

### 8.5 Codec registries

Every mirror module emits two module-level constants, exported, that the substrate's worker uses for `CallRuntimeMethod` dispatch:

```julia
const _eigenius_decoders = Dict{String, Function}(
    "<class IRI 1>" => decode_<Class1>,
    "<class IRI 2>" => decode_<Class2>,
    ⋮
)

const _eigenius_encoders = Dict{DataType, Function}(
    <Class1> => encode_<Class1>,
    <Class2> => encode_<Class2>,
    ⋮
)
```

Both maps cover every concrete class in the mirror's closure (per §3.1), in `struct_order` (the field-dependency topological order, §3.3). The decoder map keys on the **class IRI** because decode dispatch reads the input dict's `is_a` list. The encoder map keys on the **concrete struct type** because encode dispatch reads `typeof(value)` after the handler returns.

Both constants are exported alongside the struct + codec function names so a worker walking `Base.loaded_modules` can find them by `isdefined(mod, :_eigenius_decoders)` without per-module knowledge.

#### Worker-side discovery contract

The dispatch worker (D26 §8.1) building its decoder/encoder tables MUST iterate `Base.loaded_modules` rather than `names(Main; imported=true)`:

- `using SomeMirror` brings the mirror's *exports* (the `_eigenius_decoders` / `_eigenius_encoders` constants themselves) into the calling scope, but the mirror module is not added to `Main`'s name table by `imported=true`.
- Iterating `Base.loaded_modules` finds every loaded mirror package's registry directly, regardless of which scope `using`-imported it.

The worker's discovery walk is built **fresh per dispatch** (not cached at boot) so a mirror module loaded by a setup script lands in the registry immediately on the next `CallRuntimeMethod`. The cost is one `Dict` allocation per dispatch, which is negligible against the typed-call latency budget.

#### World-age rule (`Base.invokelatest`)

When a `RunRuntimeScript` precedes a `CallRuntimeMethod` and the script defines or `using`-imports a mirror module, the decoder/encoder methods land in a *newer* Julia world than the dispatch worker's accept loop. Calling them directly from the loop's older world raises a `MethodError` (`world_age` mismatch).

The worker MUST therefore invoke discovered codecs through `Base.invokelatest`:

```julia
decoded = Base.invokelatest(decoders[class_iri], m)
output_payload = Base.invokelatest(encoders[typeof(result)], result)
```

Same applies to handler invocation: the user's typed handler may be defined post-boot (e.g. by an institution's `using` of its handler package), so the worker invokes it via `Base.invokelatest` too. The performance cost is a few hundred nanoseconds per dispatch — irrelevant against typed-call latency.

This rule is generator-level only by extension: the generator emits codecs that work the same way they always have; it's the **worker contract** that must call them via `invokelatest`. Pinned here because future generator versions adding new codec entry points (e.g. embedded-resource decoders) need to know that the worker integration depends on this calling convention.

## 9. Validating constructors

Constraint properties on the property definition produce inline validation calls. The full set of constraints v1 supports:

| Constraint property | Validator call (in source order below) |
|---|---|
| `core:min_value` | `validate_min_value(:<field>, <field>, <numeric literal>)` |
| `core:max_value` | `validate_max_value(:<field>, <field>, <numeric literal>)` |
| `core:min_length` | `validate_min_length(:<field>, <field>, <integer literal>)` |
| `core:max_length` | `validate_max_length(:<field>, <field>, <integer literal>)` |
| `core:pattern` | `validate_pattern(:<field>, <field>, "<escaped pattern string>")` |
| `core:format` | `validate_format(:<field>, <field>, <format symbol>)` |

Validators are emitted in this fixed order regardless of declaration order on the property.

### 9.1 Numeric literal rendering

`min_value` / `max_value` are rendered as Julia `Float64` literals in all cases — `0` becomes `0.0`, `100.0` stays `100.0`, `0.5` stays `0.5`. The validator's parameter is typed as `Real`, so an integer would also work, but pinning `Float64` rendering keeps the generated source byte-identical regardless of whether the chain author wrote `0` or `0.0`.

`min_length` / `max_length` are rendered as Julia integer literals (no decimal point). The kernel constrains both to `core:integer` already.

### 9.2 Pattern handling

The pattern string is rendered as a Julia-escaped double-quoted string literal (backslashes doubled, double quotes escaped, newlines as `\n`, `\$` escaped to suppress Julia's string interpolation). The pattern is passed *verbatim* to `validate_pattern`; anchoring is the validator's job (§9.4).

### 9.3 Format symbol rendering

If the property's `core:format` is `urn:eigenius:core:formats:<name>`, the format argument is the Julia symbol `:<name>`. v1 recognised values: `:date`, `:datetime`, `:time`, `:iri`, `:uuid`, `:regex` — matching the core ontology's `core:formats:*` enumeration.

A `core:format` IRI **outside** the `urn:eigenius:core:formats:` prefix is **passed through to the validator with the full IRI as the symbol value** (`:<full IRI>`). The validator MUST raise on unknown formats; it does not silently pass. Generator behavior of "strip prefix or pass through" lets the chain extend `core:Format` with new formats over time without a generator change being on the critical path; the validator's enumeration is the single point that decides which formats are honoured at runtime.

### 9.4 Validator semantics (delegated to `EigeniusJuliaCommon`)

The validators called by generated source live in [`julia/common/EigeniusJuliaCommon/src/EigeniusJuliaCommon.jl`](../../julia/common/EigeniusJuliaCommon/src/EigeniusJuliaCommon.jl). Their semantics, pinned here so the spec is closed:

- `validate_min_value` / `validate_max_value`: compare-by-value; raises `ArgumentError` on out-of-range. NaN comparison follows IEEE 754 (NaN compares false against both bounds → both raise). Spec deliberately does not pin a NaN policy beyond IEEE 754; users with NaN-significant data should use a separate `is_finite` constraint.
- `validate_min_length` / `validate_max_length`: dispatched via `Base.length`. For `String`, this is character count (`length` = `lastindex` for ASCII; codepoint count for Unicode). For `Vector`, this is element count. Note that Julia's `length` on a `String` is **codepoint count, not byte count** — a multi-byte UTF-8 character contributes 1 to length. Spec uses Julia's `length` semantics; chain authors targeting byte-length checks must use `core:pattern` instead.
- `validate_pattern`: **fully-anchored** match. The validator constructs the regex as `Regex("^(?:" * pattern * ")\$")` and tests with `occursin` — a value matches iff the entire value matches the pattern. This matches the kernel-side validator (kernel/src/validation/mod.rs:429) which uses `^(?:pattern)$` framing as well.
- `validate_format`: dispatch on the format symbol. Each known format has a purpose-built check (regex for `:date`/`:datetime`/`:time`/`:iri`/`:uuid`; recompile-the-pattern for `:regex`). Unknown formats raise `ArgumentError`.

### 9.5 Regex syntax — portability boundary

Pattern strings appear in two places at validation time: the kernel-side validator (Rust `regex` crate) and the Julia-side validator (Julia `Regex`, PCRE-derived). The two engines accept overlapping but non-identical syntax. v1 pins the **portable subset** as the ECMA-262 features supported by both:

- Character classes (`[a-z]`, `[^abc]`, `\d`, `\w`, `\s`, `.`)
- Anchors (`^`, `$`, `\b`, `\B`)
- Quantifiers (`*`, `+`, `?`, `{n}`, `{n,}`, `{n,m}`, lazy `??`/`*?`/`+?`)
- Alternation (`a|b`)
- Groups: capturing `(…)`, non-capturing `(?:…)`, named `(?P<name>…)` (Rust style — Julia accepts both `(?P<…>)` and `(?<…>)`)
- Escapes (`\.`, `\\`, `\n`, `\t`, hex `\xNN`, Unicode `\uNNNN`)

The following PCRE features are **NOT** in the portable subset and MUST NOT be used in Eigon `core:pattern` strings:

- Lookahead / lookbehind (`(?=…)`, `(?!…)`, `(?<=…)`, `(?<!…)`)
- Backreferences (`\1`, `\k<name>`)
- Possessive quantifiers (`*+`, `++`, `?+`, `{n,m}+`)
- Atomic groups (`(?>…)`)
- Conditional patterns (`(?(1)…|…)`)
- POSIX collation classes (`[[:upper:]]` style)

Patterns using non-portable features pass the Julia-side validator but fail kernel-side validation (or vice versa for Rust-only features). The generator does not statically analyse pattern syntax in v1 — it's a chain-author responsibility to stay in the portable subset. Static lint of patterns is a future-work item; an implementation would live alongside the kernel's `core:pattern` validator, not in the generator.

## 10. Determinism and integrity chain

### 10.1 Determinism

Same `(generator binary, source layer, seed class IRIs)` produces byte-identical output. Sources of determinism:

- BTreeMap is used for every property iteration in the kernel's resource representation.
- Closure walk uses a sorted worklist seeded from sorted seed IRIs.
- Topological sort visits classes in BTreeMap key order, breaking ties by IRI.
- `Vector` of `class_types` IRIs is sorted before `Union` rendering (§4).
- File contents in the `LibraryContent::Embedded` archive are emitted in declaration order (`Project.toml`, then `src/EigeniusMirror.jl`); the substrate's hash function (§10.2) sorts by path for the digest.
- No timestamp, hostname, machine state, or wall-clock value appears in the output. Timestamps are recorded on the **resource** (`generated_at` is recommended, not required), not in the file.

### 10.2 Integrity chain

The `RuntimePackageMirror` resource the generator commits carries three pinned identifiers:

- `generator_identifier` = `"eigon-julia-gen"`. Fixed for this generator.
- `generator_version` = the eigenius-julia crate's `Cargo.toml` version. Synthesised at compile time via `env!("CARGO_PKG_VERSION")`.
- `generator_content_hash` = `sha256:<hex>` where the hex is the SHA-256 digest of `"eigon-julia-gen:<version>"`. v1 uses this string-derived hash as a v1 placeholder; a future spec version (post 19a.4) replaces it with the SHA-256 of the generator's compiled binary or its `Cargo.lock` digest. The shape (`^sha256:[a-f0-9]{64}$`) matches the ontology pattern on the property regardless.

The `library_content_hash` is the SHA-256 over a length-prefixed framing of the library archive's bytes, as defined in the [substrate Rust code](../../crates/eigenius-julia/src/mirror_gen.rs):

```
For each (path, content) pair in path-sorted order:
  big-endian u64 (path.len()) || path || big-endian u64 (content.len()) || content
```

The hash digests the full archive — both `Project.toml` and `src/EigeniusMirror.jl` contribute. Length prefixes prevent collisions where a path/content swap would otherwise produce a degenerate identical concatenation.

### 10.3 Mirror IRI

The committed `RuntimePackageMirror` resource's `@id` is derived from the `library_content_hash`:

```
urn:eigenius:runtime:mirror:julia:<first 16 hex chars of the digest>
```

A 16-hex-char (64-bit) prefix is large enough for collision safety in the practical generator-output universe. The full hash stays on `library_content_hash` for full-precision integrity checks. Two byte-identical mirrors produce identical IRIs — that's intentional, lets the chain dedupe.

## 11. v1 supported subset and planned extensions

### 11.1 v1.2 supported subset

A class declaration is in the v1.2 supported subset iff **all** of the following hold:

- All its `requires` and `recommends` properties have `data_type` in the §4 table (excluding the empty-`class_types` case for `resource` / `resource_array`).
- `class_types` lists are non-empty when used.
- `element_type` for `value_array` is in `{string, integer, float, boolean, json}`.
- The closure does not contain a cycle in property `class_types` references (§3.3).
- The class's `subclass_of` chain has at most one parent per class (no multi-supertype, §3.2) and is acyclic.
- The transitive field set (own + inherited via `subclass_of`) has unique property `short_name`s. Two distinct property IRIs with the same `short_name` produce a duplicate Julia struct field — rejected. The reserved `_id` slot counts in this check; properties declared with `short_name = "_id"` are rejected at resolution time.
- All class and property `short_name` values are valid Julia identifiers (alphanumeric + underscore, leading non-digit). Properties with `short_name = "_id"` are rejected as reserved (§7.2 / §8.4).
- Format IRIs on `core:format` are either standard (`urn:eigenius:core:formats:<name>`, rendered as `:<name>`) or any other IRI that the validator can dispatch on (rendered as `Symbol("<full IRI>")`, §9.3). The validator MUST raise on unknown formats; the generator does not statically check this.
- The mirror module exports `_eigenius_decoders` (class IRI → `decode_<C>`) and `_eigenius_encoders` (concrete struct type → `encode_<C>`) constants per §8.5. These are required for v1.2 conformance — workers depend on them for `CallRuntimeMethod` dispatch.

A class outside the v1.2 supported subset produces `MirrorGeneratorError::UnrepresentableClass` with a message naming the offending class and the rule it violated.

### 11.2 Planned extensions

These are part of the long-term D27 §3.3 contract but require generator features that have not yet been implemented. Each is explicitly out-of-scope for the current spec version; the spec version that includes them aligns with the implementation milestone.

**Substrate-side epistemic category stamping** — landed as part of Phase 19a.4 / 19c-as-built (the substrate's facade now stamps `urn:eigenius:reflection:DerivedResource` on every runtime output's `is_a`, alongside the structural class). Pinned in this spec at §8.4 ("multi-`is_a` is delegated to the substrate, not preserved by the mirror") with the implementation in `runtime-substrate/src/facade.rs::stamp_derived_epistemic_category`.

## 12. Spec versioning

This document is a draft v1 of D29. Every change to the contract is a spec version bump:

- **Patch versions (1.0.x)** — clarifications that don't change generator output or the integrity chain. Existing mirrors remain valid against the new patch.
- **Minor versions (1.x.0)** — additive features (new `data_type` mappings, new validators, new closure rules) where pre-bump generator output remains a valid subset of post-bump expected output.
- **Major versions (2.0.0)** — breaking changes that re-shape existing output. Existing mirrors become invalid; chain audits must use the spec version pinned by the `generator_version` on the mirror resource.

The `generator_version` property on `RuntimePackageMirror` resources implicitly anchors a spec version: the generator commits to producing output matching the spec version in force at its release, and the spec retains the prior version's text in its history (git, in this repository) for audit replay.

D29 v1.2 is the spec version for `eigenius-julia 0.1.x` from Phase 19a.4 onward. v1.2 adds the codec-registry constants (§8.5) and the world-age `Base.invokelatest` rule that the worker-side `CallRuntimeMethod` dispatcher depends on. v1.1 (Phase 19a.3.d) closed the structural-translation gap items (subclass hierarchy, `_id` round-trip, polymorphic `class_types`, format IRI passthrough, pattern anchoring, cycle detection, short_name uniqueness, multi-`is_a` reframing). v1 was the original draft authored alongside 19a.3.c that pinned the subset shipped at that milestone. Bumps follow as the implementation milestones in §11.2 land.

## 13. Open questions

These are decisions the spec deliberately defers; resolving them produces a v1.x or v2 bump.

- **Numeric type widening.** Should `Int64` fields decode `Int32` values from CBOR transparently, or raise? v1 raises (Julia's strict typing); a quieter widening policy would match Eigon's intent of "integer is integer" but adds boundary surface.
- **`Vector{Float64}` semantics for NaN.** Length-validated arrays containing NaN currently pass length checks. Whether a separate "no-NaN" predicate belongs in this spec or in a per-institution validator is open.
- **String encoding in CBOR.** Eigon-CBOR uses UTF-8; Julia's `String` is UTF-8. v1 assumes round-trip is identity. Rare invalid-UTF-8 inputs (kernel-level corruption) are out of scope.
- **`recommended` field with no validator and `nothing` default.** The current emission produces `field::Union{T, Nothing} = nothing` which is unambiguous; whether a future spec version should require a different sentinel for "explicitly absent" vs. "never set" is open and probably belongs in the kernel's `Value` model, not D29.

These items are surfaced for review but do not block v1 conformance — generator implementations and the chain agree by following v1's pinned defaults.
